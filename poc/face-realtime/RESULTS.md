# PoC 결과 기록

단계별 측정 결과를 모아 둡니다. 5단계(결과 캡처 + 사용 기술 정리)의 재료입니다.

## 실행 환경
- Windows 네이티브 Python 3.14 (`C:\dev\face-realtime`). WSL에서는 웹캠이 보이지 않아 Windows에서 실행했습니다.
- 노트북 내장 웹캠, 640×480
- 측정일: 2026-10-03

---

## 1단계: AI 분석 지연

**방법**: 웹캠 프레임 1장 → JPEG → Gemini API로 "고개 방향·시선·표정을 JSON으로" 요청하는 과정을 10회 반복했습니다 (`step1_ai_latency.py`).

### 결과: `gemini-3.5-flash-lite` (저장본)

| 항목 | 평균 | 최소 | 최대 |
|---|---|---|---|
| (a) 캡처+인코딩 | 0.008초 (8ms) | 3ms | 41ms |
| (b) API 응답 | **2.07초** | 1.47초 | 4.04초 |
| (c) 전체 | **2.08초** | 1.47초 | 4.05초 |

- 원본: [results/ai_latency.csv](results/ai_latency.csv)
- 캡처: [results/ai_latency_capture.png](results/ai_latency_capture.png)
- 같은 모델로 한 번 더 측정했을 때는 평균 2.51초(최소 1.40초, 최대 3.97초)였습니다.

### 모델별 시도 기록

| 모델 | 결과 |
|---|---|
| `gemini-2.5-flash` (원래 계획) | 404: 신규 사용자는 쓸 수 없음 |
| `gemini-3.8-flash` (API가 안내한 모델) | 성공한 3회가 각각 40.5초, 23.3초, 21.5초. 503(서버 혼잡)이 7번 나서 측정 중단 |
| `gemini-3.5-flash-lite` | 10회 모두 성공. 평균 2.1~2.5초 |

### 해석
- **지연의 99% 이상이 API 응답 대기입니다.** 웹캠 캡처와 인코딩은 10ms 안팎이라 거의 영향이 없습니다.
- **처리 속도는 약 0.4~0.5 FPS입니다.** 실시간 영상(30 FPS, 한 프레임에 약 33ms)과 비교하면 60~75배 느립니다.
- **응답 시간이 고르지 않습니다.** 최소와 최대가 약 2.8배 차이 나고, 모델과 서버 상황에 따라 수십 초가 걸리거나 아예 실패하기도 했습니다.
- **3단계 규칙에 쓸 수 없습니다.** "고개 20° 이상 2초 유지" 같은 규칙은 판단 한 번에 1.5~4초가 걸리면 판정할 수 없습니다. 실시간 탐지는 로컬에서 도는 모델(2단계 MediaPipe)이 맡아야 합니다.
- 표정 같은 정성적인 판단("골똘히 생각하는 표정" 등)은 AI가 더 풍부하게 해 줍니다. 다만 실시간 경로에는 넣기 어렵고, 가끔 보조로 쓰거나 면접이 끝난 뒤 리포트를 만들 때 쓰는 게 맞아 보입니다.

## 2단계: MediaPipe Face Landmarker

**방법**: 웹캠 영상을 거울 모드로 받아 FaceLandmarker(VIDEO 모드)로 얼굴 점 478개를 찾고, 회전 행렬에서 Yaw·Pitch·Roll을 계산했습니다. 깜빡임·미소 점수도 함께 표시합니다 (`step2_face_landmarks.py`).

### 사진으로 미리 확인한 것 (WSL, 1단계 캡처 사진 사용)
| 입력 | Yaw | Pitch | Roll |
|---|---|---|---|
| 정면 사진 | +1.1° | +1.8° | +0.0° |
| 좌우 반전 | −2.4° | +1.1° | −0.6° |
| 반시계 방향으로 15° 회전 | +1.3° | +2.7° | **+14.9°** |

- 정면일 때 0° 근처가 나오고, 사진을 15° 돌리면 Roll이 약 15° 나옵니다. 각도 계산은 맞습니다.

### 웹캠 실측 (Windows, 2026-10-03)
`c` 보정 없이 측정했습니다. 정면의 원래 값이 Yaw −2°, Pitch +2° 정도라 보정 전후 차이는 작습니다.

| 동작 | Yaw | Pitch | Roll | 깜빡임 L / R | 미소 |
|---|---|---|---|---|---|
| 정면 (캡처) | −2.2° | +2.2° | 0.0° | 0.04 / 0.02 | 0.00 |
| 고개 왼쪽 | **−40.9°** | −13.1° | +14.1° | 0.19 / 0.18 | 0.00 |
| 고개 오른쪽 | **+30.6°** | −16.2° | −17.8° | 0.36 / 0.02 | 0.00 |
| 고개 숙임 | +3.0° | **+17.6°** | −2.5° | 0.09 / 0.04 | 0.00 |
| 미소 | −4.0° | +6.4° | −0.2° | 0.11 / 0.05 | **0.82** |
| 눈 뜸 | −1.6° | −0.8° | −0.4° | 0.06 / 0.02 | 0.00 |
| 눈 감음 | −0.8° | −2.5° | −1.8° | **0.78 / 0.71** | 0.00 |

- 캡처: [results/step2_landmarks.png](results/step2_landmarks.png)
- 기록: [results/step2_angles.csv](results/step2_angles.csv). 69초 동안 2,032프레임, **약 29.5 FPS**(프레임 간격 33.9ms)로, 웹캠 최대 속도(30 FPS)를 따라갔습니다.

### 확인된 것
- **부호**(거울 화면 기준)
  - Yaw: **− = 왼쪽, + = 오른쪽**
  - Pitch: **+ = 숙임(아래)**
  - Roll: + = 화면에서 반시계 방향으로 기울임
- **고개를 좌우로 돌리면 Pitch는 −13~−16°, Roll은 ±14~18°가 함께 움직입니다.** 고개를 돌릴 때는 Pitch가 숙임과 반대 방향(−)으로 가므로, 3단계의 "고개 숙임" 판정(Pitch +)을 잘못 일으키지 않습니다. 좌우 판정은 Yaw만, 숙임 판정은 Pitch만 쓰면 됩니다.
- **눈 깜빡임**: 뜬 상태는 0.11 이하, 감은 상태는 0.7 이상으로 잘 나뉩니다. 안경을 써도 문제없었습니다. 다만 기록에서 깜빡임 횟수를 세어 보면 기준값에 따라 결과가 달라집니다(69초 동안 0.4 기준 17회, 0.5 기준 15회, 0.6 기준 11회). 3단계에서 기준값을 정해야 합니다.
- **미소**: 0.00과 0.82로 분명하게 구분됩니다.
- **1단계와 비교**: Gemini는 한 장에 약 2초(0.5 FPS)였고, MediaPipe는 웹캠 최대 속도인 30 FPS를 그대로 따라갑니다. 정확한 처리 시간(ms)은 4단계에서 측정합니다.

## 3단계: 규칙 기반 탐지

**방법**: 2단계의 각도와 깜빡임 점수를 규칙으로 판정합니다 (`step3_coaching.py`, 테스트 `test_step3_rules.py` 20개).

### 기준값과 근거
| 규칙 | 기준 | 근거 (2단계 실측) |
|---|---|---|
| 고개 돌림 | \|Yaw\| ≥ 20°, 2초 | 실제로 돌렸을 때 30~41° |
| 고개 숙임 | Pitch ≥ 15°, 2초 | 꽤 숙였을 때 +17.6°. 20°로 잡으면 놓침 |
| 깜빡임 과다 | 1분에 25회 초과 | 평소 깜빡임은 1분에 15~20회 정도 |
| 얼굴 이탈 | 2초 동안 얼굴 없음 | — |

### 깜빡임 세는 기준 정하기 (69초 기록 분석)
- **점수 분포**: 두 눈 평균 점수가 0~0.2(뜸, 1,687프레임)와 0.7~0.8(감음, 108프레임)로 뚜렷하게 나뉩니다.
- **고개를 30~40° 돌리면 눈을 뜨고 있어도 점수가 0.2~0.28까지 올라갑니다.** 그래서 "뜸" 기준을 0.2로 낮추면 고개를 돌린 동안 "감은 상태"에서 빠져나오지 못하고, 다음 깜빡임을 놓칩니다. 0.3이 적당합니다.

| 감음 / 뜸 기준 | 센 횟수 |
|---|---|
| 0.5 / 0.3 | 15회 |
| 0.5 / 0.2 | 13회 (고개 돌린 구간에서 놓침) |
| 0.6 / 0.2 | 10회 |

- **일부러 눈을 감은 1.4초와 2.0초 구간이 깜빡임으로 세어지고 있었습니다.** 보통 깜빡임은 0.1~0.4초이므로, 0.5초 넘게 감은 것은 세지 않게 했습니다.
- **결정**: 감음 ≥ 0.5, 뜸 < 0.3, 감은 시간 ≤ 0.5초 → 이 기록에서 **13회**(약 11회/분)로 셉니다.

### 자동 보정에서 발견한 문제
- 처음에는 "시작 후 2초 평균"을 정면으로 잡았습니다. 그런데 2단계 기록은 시작하자마자 고개를 왼쪽으로 돌린 상태라, **Yaw −25.6°가 정면으로 잡혔습니다.** 그 결과 이후 정면을 볼 때 "정면을 보세요"가 8번 잘못 떴습니다.
- **수정**: 카메라 기준 좌우 15° 이내이고 3° 넘게 흔들리지 않는 2초 구간이 나올 때까지 기다립니다. 다시 재생해 보니 보정은 정면 구간(21.5초)에서 확정됐고(Yaw +2.1°), 잘못된 경고는 0건이었습니다.

### 2단계 기록 재생 결과 (보정 없이 카메라 기준 각도로)
- 왼쪽(8~13초)과 오른쪽(15~17초)으로 돌린 구간에서 "정면을 보세요"가 떴습니다.
- 숙인 구간(23~25초)에서 "고개를 드세요"가 떴습니다.

## 4단계: 처리 속도 비교

**방법**: 3단계 코칭 화면을 그대로 띄우고, 보정 후 30초 동안 프레임별 구간 시간을 쟀습니다. 그 결과를 1단계 Gemini 결과와 비교했습니다 (`step4_benchmark.py`).

### 웹캠 실측 (Windows, 2026-10-03)
보정을 마친 뒤 30초 동안 **902프레임**을 측정했습니다 ([results/step4_frames.csv](results/step4_frames.csv)).

| 구간 | 평균 | 중앙값 | p95 | 최대 (ms) |
|---|---|---|---|---|
| ① 캡처(웹캠 대기) | 8.1 | 3.2 | 22.5 | 55.9 |
| ② 얼굴 분석 | 15.2 | 15.3 | 21.2 | 24.5 |
| ③ 규칙+그리기 | 0.3 | 0.2 | 0.4 | 15.1 |
| **④ 처리 합계(②+③)** | **15.4** | **15.6** | **21.5** | **31.8** |

- **화면 FPS 30.0**: 웹캠 최대 속도를 그대로 따라갔습니다.
- **처리 가능 FPS 약 65**: 웹캠이 더 빠르다면 초당 65프레임까지 처리할 수 있다는 뜻입니다.
- **한 프레임에 주어진 시간(30 FPS 기준 33.3ms)을 넘긴 프레임은 902개 중 0개**입니다. 가장 느렸던 31.8ms는 첫 프레임으로, 경고 글자를 처음 그릴 때 준비 시간이 들어간 값입니다.
- **규칙과 그리기(③)는 0.3ms로 거의 공짜입니다.** 처리 시간의 98%가 얼굴 분석(②)입니다.
- 얼굴 분석 시간은 약 11ms와 약 18ms 두 무리로 나뉩니다. 웹캠 대기(①)가 길었던 프레임에서 분석이 빨랐는데, CPU를 웹캠 드라이버와 나눠 쓰기 때문으로 보입니다. 어느 쪽이든 33ms 안에 들어옵니다.

### 결론
- 실시간 코칭(1초에 30번 판정)은 **로컬 MediaPipe + 규칙**으로 충분합니다. 한 프레임에 주어진 시간 33ms 중 약 15ms만 씁니다.
- Gemini 같은 비전 AI는 판정 한 번에 2초가 걸리고 서버 상태에 따라 실패하기도 해서, 실시간 경로에는 맞지 않습니다. "골똘히 생각하는 표정"처럼 정성적인 해석이 필요한 부분에 가끔 보조로 쓰거나, 면접이 끝난 뒤 리포트를 만들 때 쓰는 것이 적합합니다.
